AMIGO -- running a file through, copy-paste commands
====================================================

For the MS Amlin POC VM. Setup is done: the environment is configured,
the schema is applied and check_credentials.py passes against the live
tenant, so those steps are no longer here.

Run from the tree root -- the one holding config\ and .env. Paths below
assume C:\Users\GDSDRA\OneDrive - MS Amlin\_Projects\POC; change them if
yours differs.

Each step says what to expect. If a step does not produce it, stop there
rather than running the next one.


-----------------------------------------------------------------------
STEP 1 -- one file, dry run, no vendor calls
-----------------------------------------------------------------------
Run these ONE AT A TIME and read each result before the next. Any batch
id will do; SMOKE01 is used here so it is obvious later what it was for.

--- 1a. See what is actually on the share ------------------------------
plan registers everything matching *.bak unless capped, and it recurses
into subfolders. Look before you scan, and pick a SMALL file for the
first pass -- the first real upload should not be a 90 GB RDM.

  Get-ChildItem "\\sriskpd0001\Backup\Silviu" -Filter *.bak -Recurse | Select-Object Name, @{n='GB';e={[math]::Round($_.Length/1GB,2)}}

RatCat's backup process runs independently of AMIGO, so make sure
whatever you point at has FINISHED being written. plan records size and
last-write time at discovery and compares them again after staging; a
file still growing will fail there rather than here.

--- 1b. plan -----------------------------------------------------------
migration-hub plan --batch SMOKE01 --max-files 1

EXPECT: registered 1 new file(s) into batch 'SMOKE01' from \\sriskpd0001\...

Read-only and idempotent -- re-running never resets progress on rows
that already exist, so it is safe to repeat. Files are taken in sorted
order, so --max-files 1 picks the same one every time.

If it registers 0, nothing under source_root matches *.bak. Check the
path and the pattern in config\prod.json.

--- 1c. validate -------------------------------------------------------
migration-hub validate --batch SMOKE01

EXPECT: validated 1 file(s): 1 VALIDATED, 0 REJECTED

This is the step most likely to reject something. It checks the file
exists, is a file, ends in .bak, is not zero-length, and that the target
exposure name derived from the filename is valid. A rejection names the
file and the reason; an unusual filename is the usual cause.

--- 1d. stage ----------------------------------------------------------
migration-hub stage --batch SMOKE01

EXPECT: staged 1 file(s) in place (no copy)

"in place" because stage_locally is false -- nothing is copied and the
upload reads straight from the share. A copy would need somewhere to put
35 TB.

--- 1e. run (still a dry run) ------------------------------------------
migration-hub run --batch SMOKE01 --max-files 1

EXPECT: a per-file outcome line, then a running total.

With dry_run true this makes NO vendor calls and returns the file to
STAGED unchanged. It deliberately does not mark the batch RUNNING
either, so the batch does not read as in-progress forever.

--- 1f. confirm --------------------------------------------------------
migration-hub status --batch SMOKE01

The counts should reflect what happened. Nothing has left the building.


-----------------------------------------------------------------------
STEP 2 -- the real thing
-----------------------------------------------------------------------
Only once step 1 is clean.

--- 2a. Pause OneDrive sync -------------------------------------------
The registry lives on a synced path. A sync client rewriting the file
from another process is how SQLite gets a torn write, and the failure is
a corrupted registry rather than an error. Pause sync for the duration
of the run.

--- 2b. Back up the registry ------------------------------------------
scriptsackup_registry.bat

Writes a dated VACUUM INTO snapshot -- a consistent copy of a live
database, which a plain file copy is not. Set MIGRATION_HUB_BACKUP_DIR
in .env to send it off this machine, or pass a folder as the argument.

--- 2c. Go live --------------------------------------------------------
In config\prod.json set:

  "dry_run": false

then run ONLY this again:

migration-hub run --batch SMOKE01 --max-files 1

Watch it move STAGED -> UPLOADING -> UPLOADED -> IMPORTING -> VERIFYING
-> COMPLETED. The import is polled, so IMPORTING can sit for a while:
poll_interval_seconds is 60 and max_poll_minutes is 360.

Leave max_concurrent_uploads and max_concurrent_imports at 1. Three devs
against this tenant at 1 each is already three concurrent uploads.

--- 2d. Put the safety catch back --------------------------------------
Set "dry_run": true again in config\prod.json, so the next command is
not accidentally live. Resume OneDrive sync.


-----------------------------------------------------------------------
WHY DID A FILE FAIL? -- reading last_error
-----------------------------------------------------------------------
ABANDONED means the error was judged NON-RETRYABLE, or attempts ran out.
On a first attempt it is the former: something about this file or its
path, not a transient problem worth retrying.

`status` prints only the state histogram, so the reason has to come from
the registry. Both of these are read-only.

--- every file, with its error ----------------------------------------
python -c "import sqlite3; c=sqlite3.connect('registry.db'); [print(r) for r in c.execute('SELECT file_id, source_database, state, attempts, last_error FROM migration_file')]"

--- the full audit trail, newest last ----------------------------------
Every transition, who made it and why. This is what says WHICH STEP
failed, which last_error alone does not.

python -c "import sqlite3; c=sqlite3.connect('registry.db'); [print(r) for r in c.execute('SELECT event_id, file_id, from_state, to_state, actor, detail FROM migration_event ORDER BY event_id')]"

--- what the source row actually recorded ------------------------------
plan captures size and last-write time at discovery and compares them
after staging, because RatCat writes to the share independently of
AMIGO. A file still being written when it was discovered fails here.

python -c "import sqlite3; c=sqlite3.connect('registry.db'); [print(r) for r in c.execute('SELECT file_id, source_path, size_bytes, source_last_write, target_exposure_name FROM migration_file')]"

--- can this machine actually read the file? ---------------------------
Under dry_run no vendor call happens, so a first-attempt failure is
local: the share not reachable from this account, a permissions problem,
or the file changed since discovery. Substitute the source_path printed
above.

  Get-Item "\\sriskpd0001\Backup\Silviu\<name>.bak" | Select-Object Length, LastWriteTime

--- once the cause is fixed --------------------------------------------
ABANDONED files are requeued to STAGED by retry, the same as FAILED:

migration-hub retry --batch SMOKE01

-----------------------------------------------------------------------
ConnectionClosedError ON THE S3 ENDPOINT -- is S3 reachable?
-----------------------------------------------------------------------
If last_error names an *.s3.amazonaws.com URL, the upload reached the
point of sending bytes and the connection was closed underneath it. The
Moody's API call before it SUCCEEDED -- the audit trail shows "recorded
folder_id" -- so this is not credentials and not entitlement.

THE API HOST AND S3 ARE DIFFERENT HOSTS. check_credentials.py only ever
talks to api-euw1.rms.com, so it passes on a network that permits that
host and drops AWS. A proxy or firewall rule written for "the Moody's
API" does exactly this, and it fails at the upload step rather than at
startup.

--- 1. can this machine reach S3 at all? ------------------------------
A 403 or 404 is GOOD -- it means the request arrived. A timeout, a reset
or ConnectionClosedError is the block.

python -c "import httpx; r=httpx.get('https://rms-tenants-pe-eu-west-1.s3.amazonaws.com', timeout=15); print('reached S3, HTTP', r.status_code)"

--- 2. what proxy settings are actually in force? ---------------------
python -c "import os; [print(k, '=', os.environ.get(k)) for k in ('HTTPS_PROXY','HTTP_PROXY','NO_PROXY')]"

If HTTPS_PROXY is set, the rule behind it must permit BOTH hosts. If it
is empty and the network requires a proxy, boto3 never had one -- set it
in .env and re-run.

--- 3. the same request boto3 makes ------------------------------------
Closer to the real thing than a plain GET: same library, same signing,
same endpoint. It will report the AWS error rather than a generic one.

python -c "import boto3,botocore; c=boto3.client('s3', region_name='eu-west-1'); print(c.meta.endpoint_url)"

--- What to tell the network team --------------------------------------
Outbound HTTPS to *.s3.eu-west-1.amazonaws.com and
rms-tenants-pe-eu-west-1.s3.amazonaws.com, from this VM. Region
eu-west-1, confirmed from the credentials Moody's returns. Uploads are
signed per request with short-lived STS credentials, so the destination
cannot be narrowed to a fixed URL.

--- Why the file went to ABANDONED rather than FAILED ------------------
A closed connection is transient by nature, but it arrived as an
unrecognised error type, and unrecognised means non-retryable -- so it
skipped the retries it should have had. Worth knowing when reading the
state: ABANDONED here does not mean "this file is unmigratable".

Once the network path is open, requeue it:

migration-hub retry --batch SMOKE01

-----------------------------------------------------------------------
IF A RUN FAILS PART WAY
-----------------------------------------------------------------------
migration-hub status --batch SMOKE01     where it stopped
migration-hub retry  --batch SMOKE01     retry the FAILED files
migration-hub reap                       release a dead worker's claims

A file in FAILED is visible and retryable -- the registry is the record
of what happened, which is why it is worth backing up.

Do not retry a failed upload blindly. The design is to check the target
against Moody's platform first: a reported failure does not prove
nothing landed, and re-uploading a database that is already there
creates a duplicate.

-----------------------------------------------------------------------
IF SOMETHING LOOKS WRONG
-----------------------------------------------------------------------
Verify the copy against what was published (no network needed):

python scripts\check_copy.py --all

--all includes config-class files, which the default run skips. On this
staged transfer, files not yet copied show as EMPTY and that is
expected. What matters is that nothing you DID copy shows as DIFFER.
