MEASURE THE ESTATE -- distribution, from the sizes already in Excel
-----------------------------------------------------------------------
Nothing to do with a failing run. This closes a standing gap in RSK-0006
and needs no permission and no AMIGO.

WHY. The Direct server was measured; the RI server was not. RI's ~24 TB
across 5,848 databases is a STATED WORKING ASSUMPTION that it follows
Direct's distribution, not an observation. RSK-0006's own wording is that
the residual concern is "shape, not size" -- if RI is flatter than Direct
the total holds but the batch model changes.

--- FIRST: which server is this, and what unit? -----------------------
Both were wrong on the first attempt (2026-09-21), so check them before
reading anything into the numbers.

UNIT. The first run gave MAX = 975,415.1 and SUM/1024 = 22,408. As GB
those would be a 975 TB database and a 22,000 TB estate. The column was
MEGABYTES. Every formula below is written for MB; if yours is in GB,
divide each threshold by 1024 (92160 -> 90, and so on).

  Sanity check: MAX/1024 should read as a plausible GB figure. The
  largest database in this estate is 952.55 GB.

SERVER. That same MAX -- 975,415 MB = 952.6 GB -- is RSK-0006's recorded
largest on DIRECT, so the first sheet was Direct data, not RI. If the
sheet has a server column, filter it:

  SRISKPD0101 = Direct (already measured)
  SRISKPD0001 = RI     (the gap worth closing)

  Cross-check against RSK-0006's Direct figures: 55 databases >= 90 GB,
  17 above 200 GB, 4 above 500 GB, 11.4 TB total. If the >=512000 bucket
  below returns 4, this is Direct. Materially more, and it is both
  servers combined or something else again -- say which before anyone
  records it.

--- the two numbers that decide it (MB) -------------------------------
Direct, measured: 0.7% of the count carries 32.5% of the volume. The RI
assumption is ~2.0% of count. These two say whether that holds.

  =ROUND(100*COUNTIFS(B2:B6000,">=92160")/COUNT(B2:B6000),2)
  =ROUND(100*SUMIFS(B2:B6000,B2:B6000,">=92160")/SUM(B2:B6000),1)

--- totals (MB) --------------------------------------------------------
  =COUNT(B2:B6000)
  =ROUND(SUM(B2:B6000)/1048576,2)        TB
  =ROUND(MAX(B2:B6000)/1024,2)           GB

--- the shape, in seven buckets (MB) ----------------------------------
  =COUNTIFS(B2:B6000,"<1024")
  =COUNTIFS(B2:B6000,">=1024",B2:B6000,"<10240")
  =COUNTIFS(B2:B6000,">=10240",B2:B6000,"<51200")
  =COUNTIFS(B2:B6000,">=51200",B2:B6000,"<92160")
  =COUNTIFS(B2:B6000,">=92160",B2:B6000,"<204800")
  =COUNTIFS(B2:B6000,">=204800",B2:B6000,"<512000")
  =COUNTIFS(B2:B6000,">=512000")

The 90 / 200 / 500 GB boundaries (92160 / 204800 / 512000 MB) are
Direct's measured ones and the 200 GB working batch ceiling, so the two
servers compare line for line.

--- the heavy-lift candidates -----------------------------------------
TASK-0020 needs the largest few NAMED, not just counted. Sort descending
on B and screenshot the top 20 with their names, or:

  =ROUND(LARGE(B2:B6000,1)/1024,2)    through   =ROUND(LARGE(B2:B6000,20)/1024,2)

--- what each outcome means -------------------------------------------
  RI close to 2% of count -> the assumption holds and RSK-0006 narrows
  RI much flatter         -> the total may hold, but the batch model
                             changes: fewer outsized files, more
                             mid-sized ones to schedule
  RI much steeper         -> more databases above the 200 GB ceiling
                             than the plan allows for

--- one thing to confirm when you send them ---------------------------
Whether column B is .BAK file sizes or actual database sizes. A .BAK is
compressed by a data-dependent amount, so if these are backups the
RANKING is reliable and the absolute figures are a LOWER BOUND. If they
are real database sizes, this settles RSK-0006's half outright rather
than narrowing it -- a materially different claim, and worth being sure
which one is being made.

Send the counts AND the server and unit answers together. A distribution
attributed to the wrong server would corrupt a risk the plan depends on,
and RSK-0006's Direct figures have already been corrected once.

exposure name derived from the filename is valid. A rejection names the
file and the reason; an unusual filename is the usual cause.

-----------------------------------------------------------------------
STEP 2 -- the real thing
-----------------------------------------------------------------------
Only once step 1 is clean.

--- 2a. Pause OneDrive sync -------------------------------------------
The registry lives on a synced path. A sync client rewriting the file
from another process is how SQLite gets a torn write, and the failure is
a corrupted registry rather than an error. Pause sync for the duration
of the run.

--- 2b. Back up the registry ------------------------------------------
scripts\backup_registry.bat

Writes a dated VACUUM INTO snapshot -- a consistent copy of a live
database, which a plain file copy is not. Set MIGRATION_HUB_BACKUP_DIR
in .env to send it off this machine, or pass a folder as the argument.

--- 2c. Go live --------------------------------------------------------
In config\prod.json set:

  "dry_run": false

then run ONLY this again:

migration-hub run --batch SMOKE01 --max-files 1

Watch it move VALIDATED -> UPLOADING -> UPLOADED -> IMPORTING ->
VERIFYING -> BRIDGED; run stops there, and archiving is 2d. (It was
STAGED -> UPLOADING before 2026-09-22;
that state is gone.) The import is polled, so IMPORTING can sit for a while:
poll_interval_seconds is 60 and max_poll_minutes is 360.

Leave max_concurrent_uploads at 1. It is the number of worker threads,
and each thread carries one file through upload and import, so it caps
both. Three devs against this tenant at 1 each is already three
concurrent uploads.

--- 2d. Archive it into Data Vault -------------------------------------
migration-hub archive --batch SMOKE01

BRIDGED means the database reached Data Bridge. It is not migrated
until it is archived in Data Vault -- the bridge is the route in, the
vault is the destination. This takes it BRIDGED -> ARCHIVING ->
COMPLETED, and COMPLETED now means "in Data Vault" (ADR-0010). A failed
archive leaves it ARCHIVE_FAILED -- still on Data Bridge -- and running
this again retries the archive only, never the upload. Five years' retention from the upload date is
applied automatically.

It waits for the archive job to finish (checking every
poll_interval_seconds, up to max_poll_minutes) and then for the archive
to appear in Data Vault, so when it prints "archived 1 file(s)" the
database is confirmed there. migrate --source does this step itself.

Re-running is safe: a database that already has an archive row is
skipped rather than archived twice.

--- 2e. Put the safety catch back --------------------------------------
Set "dry_run": true again in config\prod.json, so the next command is
not accidentally live. Resume OneDrive sync.


-----------------------------------------------------------------------
THE ONE-COMMAND ALTERNATIVE -- migrate --source
-----------------------------------------------------------------------
New on 2026-09-22. Does the whole of 1b-1e and 2d in one invocation:
discover, validate, upload, import, verify, archive, reconcile, and
sign off if the run is clean.

  migration-hub migrate --source "\\sriskpd0001\Backup\Silviu" --max-files 1

WHEN TO USE WHICH. The step-by-step sequence above is for the first run
on a machine, or when something is wrong and you need to see which step
it goes wrong at. `migrate` is for once that works -- and it is the
right one for TIMING the POC, because it measures the operation the way
it will actually be run.

WORTH KNOWING:

  - The batch id is DERIVED from the source path, not supplied. Point
    at the same folder again and it is the same batch, not a new one.

  - It respects dry_run in config\prod.json. With dry_run true it runs
    discovery, validation and the upload loop with no vendor calls,
    then stops before archive/close/sign-off and says so.

  - Concurrency is settings.max_concurrent_uploads as IN-PROCESS
    THREADS, each with its own vendor adapter -- not separate processes
    as `run` used to launch. Leave it at 1.

  - A clean run signs itself off, recorded as `migration-hub-auto`.
    It never records a human's name for an automated sign-off, so the
    two are always tellable apart in the audit trail.

  - A run that closes EXCEPTIONS stops for a human to review:

      migration-hub controls history --batch <id>

IF THE DASHBOARD SAYS "Runaway risk" OR A FILE WILL NOT MOVE
-----------------------------------------------------------------------
Added 2026-09-23, after one file on this VM went upload -> 403 ->
upload 24 times in 15 minutes. The API calls panel on the dashboard is
what shows it: the call count keeps climbing while the pipeline step
does not advance.

--- watch it live (from the publish of TASK-0090) ----------------------
EASIEST: on the dashboard, select the batch and turn on Live log under
its action bar. It follows the batch's newest run log, refreshing every
2 seconds, with a Problems only filter, and warns when the log has gone
quiet while files are still outstanding.

OUTSIDE THE BROWSER: a run started from the dashboard writes to logs\ in the tree root, and
the Start migration dialog shows the exact command. For the newest log:

  Get-Content (Get-ChildItem logs\*.log | Sort-Object LastWriteTime | Select-Object -Last 1).FullName -Wait -Tail 40

One line per step and per vendor call. A refused call is a WARNING line
ending in the storage service's reason, e.g.

  18:02:12 WARNING file 7  PUT (presigned storage upload)  403  180 ms  AccessDenied

so the log usually answers "why" without the query further down. The
Streamlit window never shows any of this -- the migration runs as its
own process. Ctrl+C stops the watching, not the migration.

--- stop it first ------------------------------------------------------
Click Pause -- in the Start migration dialog, or in the batch's action
bar. The worker finishes the attempt it is on, claims nothing more, and
exits. Check a minute later that the call count has stopped rising.

Only if it keeps rising, end the migration workers (the dashboard is
left running):

  Get-CimInstance Win32_Process -Filter "name='python.exe'" | Where-Object CommandLine -match 'migration_hub.cli' | ForEach-Object { Stop-Process -Id $_.ProcessId -Force }

From the publish carrying the fix, a refused upload stops by itself
after max_attempts (3) and the file lands ABANDONED with the reason in
last_error. Before it, a 403 on the upload restaged forever.

--- then read what the vendor said -------------------------------------
Every call is in the registry, and a failed upload keeps the first 2000
characters of the storage service's reply. Run from the tree root, in
the (.venv) PowerShell window:

@'
import os, sqlite3
from dotenv import load_dotenv
load_dotenv(".env")
path = os.environ["MIGRATION_HUB_DATABASE_URL"].split(":///", 1)[1]
db = sqlite3.connect(path)
for row in db.execute("select occurred_at, method, status_code, substr(response_body, 1, 800) from api_transaction where status_code >= 400 order by transaction_id desc limit 3"):
    print(row, "\n")
'@ | python -

It prints the three most recent failed calls, newest first. For a
storage PUT the reply is XML whose <Code> says why:

  SignatureDoesNotMatch   the request sent is not the one the URL was
                          signed for (a header or the body length) --
                          our side. This was the 2026-09-23 loop: small
                          uploads did not send Content-Type, fixed in the
                          same publish. Seen again after that, send it
                          to the devs; it now fails the file at once
                          rather than retrying.
  AccessDenied            the URL or its credentials are not allowed to
                          write there -- Moody's side
  RequestTimeTooSkewed    this machine's clock is wrong; fix the clock
  ExpiredToken /          the URL really had expired -- only plausible
  Request has expired     if the upload started long after it was issued

Paste the output to the devs either way -- the Code line is what they
need. The URL itself is stored with its signature removed (TASK-0087),
so the output is safe to share.

WHY DID A FILE FAIL? -- reading last_error
-----------------------------------------------------------------------
VERDICT (2026-09-21): SOLVED -- and the answer was not in these commands.
The file failed because cli.py wired the superseded `platform/import/v1`
adapter, not because of anything about the file or its path. See ADR-0008

ABANDONED means the error was judged NON-RETRYABLE, or attempts ran out.
On a first attempt it is the former: something about this file or its
path, not a transient problem worth retrying.

`status` prints only the state histogram, so the reason has to come from
the registry. Both of these are read-only.

--- every file, with its error ----------------------------------------
python -c "import sqlite3; c=sqlite3.connect('registry.db'); [print(r) for r in c.execute('SELECT file_id, source_database, state, attempts, last_error FROM migration_file')]"

--- the full audit trail, newest last ----------------------------------
Every transition, who made it and why. This is what says WHICH STEP
failed, which last_error alone does not.

python -c "import sqlite3; c=sqlite3.connect('registry.db'); [print(r) for r in c.execute('SELECT event_id, file_id, from_state, to_state, actor, detail FROM migration_event ORDER BY event_id')]"

plan captures size and last-write time at discovery and compares them
after staging, because RatCat writes to the share independently of
AMIGO. A file still being written when it was discovered fails here.

python -c "import sqlite3; c=sqlite3.connect('registry.db'); [print(r) for r in c.execute('SELECT file_id, source_path, size_bytes, source_last_write, target_exposure_name FROM migration_file')]"

-----------------------------------------------------------------------
ConnectionClosedError ON THE S3 ENDPOINT -- is S3 reachable?
-----------------------------------------------------------------------
VERDICT (2026-09-21): S3 WAS NEVER BLOCKED. An afternoon went into this
theory and it was wrong. The real cause was the superseded adapter
(ADR-0008/0009), and Swagat's POC put a file through the same network
without difficulty.

What genuinely came out of it, and is worth keeping:
  - CERTIFICATE_VERIFY_FAILED means TLS inspection, NOT a block. The
    check below that reported it used plain httpx, which does not load
    truststore the way AMIGO does. A failure here does not imply AMIGO
    would fail.
  - TLS inspection IS in force on this VM, truststore handles it, and no
    proxy credentials are needed (access-request item 3.6, closed).

Run these only if a NEW failure names an s3.amazonaws.com URL.

If last_error names an *.s3.amazonaws.com URL, the upload reached the
point of sending bytes and the connection was closed underneath it. The
Moody's API call before it SUCCEEDED -- the audit trail shows "recorded
folder_id" -- so this is not credentials and not entitlement.

THE API HOST AND S3 ARE DIFFERENT HOSTS. check_credentials.py only ever
talks to api-euw1.rms.com, so it passes on a network that permits that
host and drops AWS. A proxy or firewall rule written for "the Moody's
API" does exactly this, and it fails at the upload step rather than at
startup.

--- 1. can this machine reach S3 at all? ------------------------------
A 403 or 404 is GOOD -- the request arrived. A timeout or a reset is a
block. CERTIFICATE_VERIFY_FAILED is NEITHER: it means you reached the
proxy and this particular command did not trust its certificate. Plain
httpx does not load truststore, so that result says nothing about
whether AMIGO can connect -- see check 2, which is the real test.

python -c "import httpx; r=httpx.get('https://rms-tenants-pe-eu-west-1.s3.amazonaws.com', timeout=15); print('reached S3, HTTP', r.status_code)"

--- 2. the same request, the way AMIGO makes it -----------------------
THIS is the one that matters. truststore routes verification through the
Windows certificate store, where the proxy's internal root already is,
and it patches the ssl layer so it covers boto3 as well as httpx.

python -c "import sys; sys.path.insert(0,'src'); from migration_hub import _tls; ok=_tls.inject(); print('truststore active:', ok, _tls.unavailable_reason or ''); import httpx; r=httpx.get('https://rms-tenants-pe-eu-west-1.s3.amazonaws.com', timeout=15); print('reached S3, HTTP', r.status_code)"

  truststore active: True  + an HTTP status  -> the path works; the upload
      failure is something else, and check 3 will show it
  truststore active: True  + CERTIFICATE_VERIFY_FAILED -> the proxy root is
      not in the Windows store, or this is a different proxy from the one
      the Moody's host goes through
  truststore active: False -> truststore did not load; the reason is
      printed beside it

--- 3. an actual S3 call through boto3 --------------------------------
Closest to the upload itself: same library, same signing, same endpoint.
Expect a credentials or access error -- that still proves the CONNECTION
works, which is what is being tested here.

python -c "import sys; sys.path.insert(0,'src'); from migration_hub import _tls; _tls.inject(); import boto3; boto3.client('s3', region_name='eu-west-1').list_buckets()"

--- 4. what proxy settings are actually in force? ---------------------
python -c "import os; [print(k, '=', os.environ.get(k)) for k in ('HTTPS_PROXY','HTTP_PROXY','NO_PROXY')]"

A rule written for "the Moody's API" covers api-euw1.rms.com and not
*.s3.amazonaws.com. They are different hosts, which is why
check_credentials.py passes and the upload does not.

--- What to tell the network team --------------------------------------
Outbound HTTPS to *.s3.eu-west-1.amazonaws.com and
rms-tenants-pe-eu-west-1.s3.amazonaws.com, from this VM. Region
eu-west-1, confirmed from the credentials Moody's returns. Uploads are
signed per request with short-lived STS credentials, so the destination
cannot be narrowed to a fixed URL.

--- Why the file went to ABANDONED rather than FAILED ------------------
A closed connection is transient by nature, but it arrived as an
unrecognised error type, and unrecognised means non-retryable -- so it
skipped the retries it should have had. Worth knowing when reading the
state: ABANDONED here does not mean "this file is unmigratable".

Once the network path is open, requeue it:

migration-hub retry --batch SMOKE01

-----------------------------------------------------------------------
IF A RUN FAILS PART WAY
-----------------------------------------------------------------------
migration-hub status --batch SMOKE01     where it stopped
migration-hub retry  --batch SMOKE01     retry the FAILED files
migration-hub reap                       release a dead worker's claims

A file in FAILED is visible and retryable -- the registry is the record
of what happened, which is why it is worth backing up.

Do not retry a failed upload blindly. The design is to check the target
against Moody's platform first: a reported failure does not prove
nothing landed, and re-uploading a database that is already there
creates a duplicate.

-----------------------------------------------------------------------
IF SOMETHING LOOKS WRONG
-----------------------------------------------------------------------
Verify the copy against what was published (no network needed):

python scripts\check_copy.py --all

--all includes config-class files, which the default run skips. On this
staged transfer, files not yet copied show as EMPTY and that is
expected. What matters is that nothing you DID copy shows as DIFFER.
