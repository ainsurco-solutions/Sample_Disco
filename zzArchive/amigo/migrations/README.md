# Schema Migrations

Alembic migrations for the registry database.

The schema is documented in
[`docs/architecture/state-model.md`](../docs/architecture/state-model.md#2-registry-schema)
and modelled in [`src/migration_hub/core/models.py`](../src/migration_hub/core/models.py).
Those three must stay in step. When they drift, the document is the one that gets
read during an incident, so it is the one that must be right.

## Usage

```powershell
alembic upgrade head                            # apply
alembic revision --autogenerate -m "add x"      # create from model changes
alembic downgrade -1                            # roll back one
```

## Rules

- **Review autogenerated migrations before committing.** Alembic's SQL Server
  support does not always produce what you meant, particularly around indexes and
  nullability.
- **Never edit an applied migration.** Add a new one.
- **Index changes on `migration_file` deserve care.** The `(state, batch_id)` index
  is the access path for the claim query, which every worker runs constantly. A
  change here is a change to the throughput of the whole migration.
- **Do not add a column that stores a credential.** The registry is designed to hold
  none ([Gate 6](../docs/operations/testing-checklist.md)).

## Initial migration

Not yet written — the models are still scaffolds. The first revision should create
`migration_file`, `migration_event`, `api_transaction`, `batch` and `batch_run`, with:

- unique constraint on `migration_file.source_path`
- unique constraint on `migration_file.target_exposure_name`
- index on `migration_file (state, batch_id)`
- foreign keys from `migration_event` and `api_transaction` to `migration_file`
- foreign key from `batch_run` to `batch`, unique on `(batch_id, run_seq)`
- **foreign key from `migration_file.batch_id` to `batch`** — see below

### The `migration_file.batch_id` constraint

`batch_run.batch_id` is a foreign key to `batch`. `migration_file.batch_id` currently
is not — it is indexed for the claim query, but nothing constrains it to an existing
batch. Add the constraint in this first revision.

Every control total on `batch_run` is derived by selecting `migration_file` rows on
`batch_id`, so a batch id typed wrongly at plan time creates rows belonging to no
batch: never claimed by a worker, absent from `source_count`, invisible in the control
record. The run then closes `CLEAN` while those files sit unmigrated — a silent
failure in the one place built to prevent silence.

One line now; a data migration afterwards, against a table with 8,000 rows and a live
audit trail hanging off it. Diagrammed in the
[registry ERD](../docs/diagrams/registry-erd.md#the-dotted-line).

`batch_run` holds signed control totals
([batch controls](../docs/operations/batch-controls.md)). A later migration that
rewrites its rows rewrites evidence that has already been accepted — treat corrections
as a new run, not an `UPDATE`.
